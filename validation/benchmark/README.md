# Simulation benchmark

This benchmark measures how well SynTangle removes **presentation tangledness**
from extant chromosome structures generated by the forward simulator.

It is deliberately separate from the future ancestral-history benchmark.
Hidden fusion/fission/inversion histories are generated and retained, but they
are not used to choose an extant layout.

## Benchmark sequence

```text
ancestor
  ↓
logged fusion / fission / inversion
  ↓
extant genomes
  ↓
hidden native presentation
  ↓
whole-chromosome permutation / reversal
  ↓
PUBLIC tangled bundle
  ↓
SynTangle
  ↓
optimized legal layout
  ↓
only then inspect hidden logs/baselines
```

The Python runner imports only the public validation-bundle tables before
optimization. Hidden files are read after the solve for descriptive benchmark
columns.

## Profiles

### Smoke

Three deterministic small cases intended for GitHub Actions.

```bash
Rscript validation/benchmark/generate_benchmark_cases.R \
  /tmp/syntangle-benchmark smoke
```

### Full historical regression

The original 27-case grid spans 3/4/5 species, 6/8/10 ancestral chromosomes,
and mild/strong/random presentation tangles. Its historical case-specific
seeds are preserved so Stage 13--15 results remain directly comparable.

```bash
Rscript validation/benchmark/generate_benchmark_cases.R benchmark_full full
```

### Paired presentation benchmark

The paired profile has the same 3/4/5 species by 6/8/10 chromosome grid, but
each biological simulation is generated **once** and reused for a
mild/strong/random presentation triplet. This creates nine biological groups
and 27 total cases.

Within each triplet:

- extant chromosome structures are identical;
- homology/block evidence is identical;
- hidden evolutionary history is identical;
- the solver random seed is identical;
- only the presentation tangle and its tangle seed differ.

Therefore any three **proven** optima in a triplet must have the same C*. The
invariance checker treats a difference as a regression.

```bash
Rscript validation/benchmark/generate_benchmark_cases.R benchmark_paired paired

python validation/benchmark/run_benchmark.py \
  benchmark_paired \
  --output benchmark_paired/benchmark_results.tsv \
  --summary-json benchmark_paired/benchmark_summary.json \
  --summary-md benchmark_paired/benchmark_summary.md

python validation/benchmark/check_paired_invariance.py \
  benchmark_paired/benchmark_results.tsv \
  --require-proven \
  --json benchmark_paired/paired_invariance.json \
  --markdown benchmark_paired/paired_invariance.md
```

A smaller three-case paired-smoke profile is used in CI.

### Scaling probe

The scale profile holds species count at four and increases ancestral chromosome
count through 12, 15, 20, and 30. Every scale point is again a controlled
mild/strong/random presentation triplet.

```bash
Rscript validation/benchmark/generate_benchmark_cases.R benchmark_scale scale

python validation/benchmark/run_benchmark.py \
  benchmark_scale \
  --output benchmark_scale/benchmark_results.tsv \
  --summary-json benchmark_scale/benchmark_summary.json \
  --summary-md benchmark_scale/benchmark_summary.md
```

This is a probe, not an assertion that 30 chromosomes is the final scaling
limit. If a case becomes bounded, retain that result rather than silently
raising caps: the first failure point is useful algorithmic evidence.

### Coupled high-complexity stress ladder

The `stress` profile deliberately increases **all three biological/search
complexity axes together**, rather than changing only one:

| Rung | Species | Ancestral chromosomes | Structural events per lineage step | Anchors/chromosome |
|---|---:|---:|---:|---:|
| 1 | 6 | 20 | 5 | 16 |
| 2 | 8 | 30 | 8 | 18 |
| 3 | 10 | 40 | 12 | 20 |

Each rung is a controlled mild/strong/random presentation triplet, giving nine
cases total. Fusion and fission counts are balanced within the high-complexity
event plans so chromosome number remains roughly stable while structural
history accumulates across increasingly many lineage steps.

```bash
Rscript validation/benchmark/generate_benchmark_cases.R \
  benchmark_stress stress

time python validation/benchmark/run_benchmark.py \
  benchmark_stress \
  --output benchmark_stress/benchmark_results.tsv \
  --summary-json benchmark_stress/benchmark_summary.json \
  --summary-md benchmark_stress/benchmark_summary.md \
  --transition-cap 250000 \
  --branch-node-cap 100000 \
  --local-restarts 4
```

Do not increase caps merely to obtain nine proofs. A bounded result is useful:
the first rung/structure that fails to prove the optimum identifies the next
solver bottleneck.

## Vector visual report

Benchmark results can be rendered as a dependency-free HTML report with
embedded vector SVG figures and optional standalone SVG copies:

```bash
python validation/benchmark/render_benchmark_report.py \
  benchmark_paired/benchmark_results.tsv \
  benchmark_paired/benchmark_report.html \
  --title "SynTangle paired benchmark" \
  --svg-dir benchmark_paired/figures
```

The report includes:

- runtime versus chromosome scale;
- controlled presentation-tangle visualization when paired groups are present;
- implicit orientation states versus actually evaluated residual-search nodes
  for branch-and-bound cases;
- a method-stage utility audit distinguishing active solver machinery from
  diagnostic, preparatory, and deferred steps;
- the complete per-case result table.

For eye-level ground truth, generate a **case gallery**. Each linked report
shows the hidden simulator-native baseline, tangled public input, optimized
layout, graph structure, and solver diagnostics:

```bash
python validation/benchmark/render_case_gallery.py \
  benchmark_stress \
  benchmark_stress/case_reports

open benchmark_stress/case_reports/index.html
```

To reduce rendering/solve time while first inspecting a new stress run, render
only the random presentation from each biological rung:

```bash
python validation/benchmark/render_case_gallery.py \
  benchmark_stress \
  benchmark_stress/random_reports \
  --modes random

open benchmark_stress/random_reports/index.html
```

## Recorded quantities

Each case records:

- input and biological fingerprints separately;
- paired biological ID and independent biology/tangle seeds where applicable;
- species/chromosome/anchor scale and planned structural events per lineage step;
- incidence-component count;
- raw incidence cycle rank;
- chromosome-signature structural cycle rank;
- structural hard-kernel count and largest kernel size;
- hidden evolutionary event count **after** solving;
- number of chromosomes deliberately moved/flipped by tangle induction;
- hidden native-presentation crossing count **after** solving;
- input, component-normalized, and optimized crossing counts;
- crossings removed by normalization and by the full solver;
- lower bound, upper bound, and optimality gap;
- proven optimum versus bounded best known;
- solver selected;
- states/nodes evaluated;
- for monotone branch-and-bound runs: implicit orientation-state count,
  orientation nodes actually evaluated, order nodes evaluated, branches pruned,
  groups forced by bounds, and memo/cache hits;
- wall time.

The hidden native presentation is a useful simulator baseline, not a claim
about a uniquely correct biological layout. A different legal layout can have
the same or lower crossing objective.

## Interpreting structural metrics

Repeated anchors supporting the same chromosome relationship can greatly
inflate raw incidence cycle rank without increasing chromosome-level
rearrangement complexity. The structural-bundle projection is therefore
reported alongside the raw graph.

However, structural projection and the bridge/articulation/2-core/biconnected
machinery are currently **diagnostic rather than optimizer inputs**. The active
solvers factor on exact incidence connected components. See
`docs/method_stage_audit.md` for the current status of each method stage.

Large benchmark outputs are working data. Commit scripts and compact summaries,
not bulk generated bundles.
